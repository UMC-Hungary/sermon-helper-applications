## Why

The app's visual language lives as ~1,600 lines of ad-hoc `<style>` blocks spread across 18 routes and 35 components, each re-deriving its own padding, radius, shadow and type scale on top of a thin set of colour variables in `src/app.css`. There is no shared component vocabulary, no documented accessibility behaviour (no keyboard maps, no focus management, no contrast budget), and light/dark is not even user-selectable — it silently follows the macOS system theme. A new design direction ("Sanctum", prototyped in `~/workspace/ui/sermon-helper-svelte`) exists and the app should move to it wholesale; doing that by hand-editing 53 files would reproduce exactly the same unmaintainable situation in new colours. Instead the design direction becomes the first consumer of a real design system — tokens, accessible primitives, written component specifications — and the app is rebuilt on top of it.

## What Changes

- Introduce a **design system** at `src/lib/ds/`: a token layer, a set of accessible primitives and composed patterns, and a written specification per component (anatomy, props API, states, tokens consumed, keyboard map, ARIA roles, acceptance criteria). Architecture follows the headless-behaviour + token-styling model (WAI-ARIA Authoring Practices for behaviour, W3C Design Tokens Community Group format for the token source of truth).
- Introduce **theme packs**: `sanctum` (the new parchment/serif direction — default) and `classic` (today's Apple-native look, retained as the migration safety net), each with a complete **light and dark** token set.
- Retint the macOS **transparent glass background** to the active theme's colours. The liquid-glass window effect, `backdrop-filter` blur/saturate values, `data-glass='false'` non-glass fallback and the `prefers-reduced-transparency` fallback all survive unchanged — only the surface tints change with the theme.
- Add **Appearance settings**: a design-theme selector and an explicit **Light / Dark / Auto** control. **BREAKING** for the current behaviour that light/dark is system-driven only; `systemTheme` becomes the input to an `Auto` mode rather than the sole source of truth.
- Add a dev-facing **component catalog** at `/design` rendering every component across all variants, states, themes and colour schemes, including a keyboard-map reference and a computed WCAG contrast report.
- **Migrate all 18 routes and 35 components** onto the design system, route by route, replacing local `<style>` blocks with design-system components and tokens.
- Act on a **component-by-component audit of the design reference against this application** (recorded in `design-coverage.md`), which establishes that only **6 of 18 routes have a design counterpart**, identifies **14 component gaps** the reference has no answer for (data table, accessible select, tabs, skeleton, empty/error/not-connected states, log stream, progress, badge, radio group, wizard, tooltip, icon set), and documents **9 breaking changes** where the reference conflicts with what the app supports today — most significantly its 4-destination mobile tab bar against the app's 10-item desktop sidebar, and its complete absence of an accent colour against the app's 79 uses of macOS `AccentColor`.
- Establish an **accessibility baseline** the system enforces: visible focus indicators, full keyboard operability, correct roles/labels, WCAG 2.2 AA contrast, honoured `prefers-reduced-motion` and `prefers-reduced-transparency`.
- Give Sanctum an **interactive accent distinct from its status colours** — the reference has no accent at all and spends its warm hues on meaning (ember for live and error, amber for warn), so an accent drawn from that range would make a focused field and a failed upload share a hue.
- **Collapse navigation to four destinations** — Dashboard, Events, Presentations, Settings — with Settings as the hub for Connectors, Connect, OBS caption, OBS devices, RF/IR, Queues, Logs and Setup. Live events becomes the "Live" filter within Events. **BREAKING** for the current 10-item sidebar, though route paths are unchanged.
- **Support mobile as a first-class target.** The navigation becomes responsive — a bottom tab bar below the mobile breakpoint, the glass sidebar above it — and every component and surface is built to work from a 360px viewport upward, with token-defined breakpoints, 44×44 touch targets, safe-area insets, reflowing tables and dialogs that present as sheets. The app is effectively non-responsive today, while the design reference is mobile-first, so the reference supplies both layouts.
- **Unify notifications into one system and forbid duplicate components.** The reference's tiered, persistent, actionable notification model is adopted; `svelte-sonner` is removed and its 40 call sites migrated; the `/errors` page is absorbed into the notification centre with its remediation and fix flows intact. **BREAKING** for the errors destination and the toast dependency. More generally, the design system provides exactly one component per concept — no component may have a twin, and superseded implementations are removed rather than left in parallel.
- **Exclude the projection output surfaces.** The presenter view (`/presenter`) and the caption overlay (`/caption`) keep their fixed presentation design and are untouched: no tokens, no theme attributes, and no observable effect from any appearance setting. Their operator-facing control screens (`/presentations`, `/obs-caption`) are migrated normally.
- **Keep both theme packs permanently selectable in a single build.** A theme pack is ~5 KB of custom properties against a 104 MB app bundle, and classic needs no fonts — so retaining it costs nothing measurable, keeps the rollback path open indefinitely, and avoids duplicating the application into per-design builds.

## Capabilities

### New Capabilities
- `design-tokens`: A layered, themeable token architecture (primitive → semantic → component tokens) authored in W3C DTCG format and emitted as CSS custom properties, covering colour, typography, spacing, radius, elevation, motion and glass surfaces, for every theme × colour-scheme combination.
- `design-system-components`: An accessible, documented component library (primitives and composed patterns) styled exclusively through tokens, with a written specification and accessibility contract per component.
- `appearance-settings`: User-facing selection and persistence of the design theme and the light/dark/auto colour scheme, applied without restart.
- `design-catalog`: An in-app catalog route rendering the full component inventory across variants, states, themes and colour schemes, with keyboard and contrast documentation, used to detect drift and verify accessibility.
- `sanctum-ui-migration`: The route-by-route conversion of the application's screens onto the design system, including the app shell, and the coverage rule that no migrated surface retains ad-hoc styling.

## Impact

- **Frontend (`/src`)**: new `src/lib/ds/` tree (tokens, primitives, patterns, docs); `src/app.css` reduced to a reset plus a token-pack import; `src/routes/+layout.svelte` rebuilt around responsive four-destination navigation and theme + colour-scheme application on `<html>`; new `src/lib/stores/appearance.ts` superseding the theme half of `src/lib/stores/system-appearance.ts`; new `src/lib/components/settings/AppearanceSettings.svelte`; new `src/routes/design/`; every in-scope route and component rewritten against the system.
- **Navigation and notifications**: `src/lib/stores/errors.ts` becomes the single notification store; `svelte-sonner` removed from `package.json` and its 40 call sites across 8 files migrated; `NavErrorBadge.svelte` replaced by a notification bell; `/errors` retired as a destination; `/live-events` retired as a destination while its path keeps working; e2e journeys that navigate via the sidebar updated.
- **Assets**: the three prototype typefaces (Cormorant Garamond, Inter Tight, Geist Mono) must be **self-hosted and bundled** — the prototype loads them from Google Fonts, which the offline desktop app and the embedded-asset release build cannot rely on. Adds woff2 subsets to `static/`.
- **Persistence**: theme and colour-scheme choices stored via the existing dual pattern in `src/lib/i18n.ts` — `localStorage` for a flash-free first paint, mirrored into the Tauri `settings.json` host store.
- **Glass / platform**: `src/app.css` glass variables, `tauri-plugin-liquid-glass` integration and the `data-glass` / reduced-transparency fallbacks are re-expressed as theme-owned tokens; macOS, Windows and Linux appearances must all be re-verified.
- **Relationship to `decouple-core-from-rendering-ui`**: independent axis. That change swaps whole frontend bundles via `ui/registry.json`; this one restyles the default UI from within. The two selectors stay distinct — Active UI (restart) vs Appearance (live).
- **Non-goals**: no change to core/server behaviour, HTTP/WS contracts, OpenAPI, Bruno collections, Zod schemas or Companion; no new runtime UI dependency (the system is authored in-repo).
- **Out of scope for the migration list**: `presenter-receiver` (native Rust renderer) and the outlined-SVG presenter output, which are not DOM surfaces.
