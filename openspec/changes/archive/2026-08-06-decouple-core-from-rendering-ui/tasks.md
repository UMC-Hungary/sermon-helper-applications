## 2. Config/secret provider abstraction

**Dropped as unnecessary for headless.** The core startup path never read `tauri-plugin-store`: all store access lives in `lib.rs::run` setup and `commands/*` (the Tauri adapter), which pass plain values in. `CoreOptions` is that seam. Revisit in phase 4 — moving connector configs onto HTTP needs server-owned config storage (DB or file), which is a different abstraction than these traits.

### Bible fetch moved into the core

- `GET /api/bible/verses?reference=&translation=` and `GET /api/bible/suggest?term=` (`server/routes.rs` → `bible.rs`). The core picks the upstream API from the translation code (`*_v2` → V2 API, else legacy), performs the request, strips markup, and returns one normalised `{ label, verses[] }` shape; the legacy `gepi` location string is parsed to chapter/verse server-side. Upstream base URLs are overridable via `METOCAST_BIBLE_V2_URL` / `METOCAST_BIBLE_LEGACY_URL`.
- The 3 `fetch_bible_*` IPC commands are gone, and `bible.rs` is now `#[cfg(desktop)]` (mobile is client-only and reaches this over HTTP).
- Frontend: `lib/utils/bible-api.ts` lost its Tauri-vs-browser fork and the CORS-proxy path — `lib/config/bible-api.ts` deleted entirely, along with the upstream API types in `lib/types/bible.ts`. New `lib/schemas/bible.ts` Zod schemas; `fetchLegacy` folded into `fetchVerses` (the one caller passed a legacy translation anyway).
- Contract surfaces: OpenAPI paths + `BiblePassage`/`BibleSuggestion` schemas + a `Bible` tag; `bruno/bible/` requests; `e2e/rest/bible.test.ts` (upstream-hitting cases run only with `BIBLE_UPSTREAM=1`); Rust unit tests for `gepi` parsing and markup stripping.
- **Upstream breakage found and fixed:** `szentiras.eu/api/idezet` (all classic verse lookups — RUF, KG, KNB, SZIT, BD, STL) started requiring `X-API-Key`. Pre-existing, not caused by the move — the old IPC path built the identical URL. Now handled by the `szentiras` connector below.

### Szentírás.eu added as a connector

- `SzentirasConfig { enabled, apiKey }` in `connectors/mod.rs`, stored in `app_settings` as `szentiras_config` and reachable through the same `GET`/`PUT /api/connectors/szentiras/config` endpoints as every other connector. It has no worker: status is Connected when a key is stored, like ATEM and Discord.
- `bible::fetch_passage` takes the key and sends it as `X-API-Key`; `routes::get_bible_passage` loads it from the config. Upstream 401/403/429 are translated into messages that say what to do. Autocomplete stays keyless (that endpoint is public upstream).
- **Bug found while testing with a real key:** szentiras.eu now returns the machine code as `JHN_3_16` (USX book code), not the old `001001016` digit packing — so *every* verse was falling back to chapter 1 with a positional verse number. `parse_gepi` handles both forms now, with unit tests for each.
- UI: connector definition (`lib/connectors/szentiras.ts`) carrying a written explanation of how szentiras.eu works, a settings block with an **Enabled** toggle and a password-masked **API key** field linking to `szentiras.eu/profile/api-keys`, stores, registry entry, dashboard branches, and en/hu locale strings.
- Verified live against the headless binary with a real key: config round-trips, status flips to connected, and `RUF`/`KG` lookups return correct chapter/verse text. The key was **not committed** — it lives only in the local DB, and I cleared it afterwards.
