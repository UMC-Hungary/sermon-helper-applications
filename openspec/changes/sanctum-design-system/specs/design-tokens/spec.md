## ADDED Requirements

### Requirement: Token values are measured from the design reference
Every token value SHALL be derived from a measurement taken from the design reference. A value present in the reference SHALL be present in the token scale at its measured value, and SHALL NOT be rounded, snapped or normalised to fit a generated or conventional scale. Where the reference uses a value only once, that value SHALL still be represented rather than approximated by a neighbouring step.

#### Scenario: Reference value is preserved exactly
- **WHEN** the reference specifies a spacing, size, height, weight or tracking value
- **THEN** a token exists carrying that exact value
- **AND** no component substitutes a different value for it

#### Scenario: Scale is not imposed
- **WHEN** the token scale is reviewed
- **THEN** its steps correspond to values observed in the reference
- **AND** no step exists solely to complete an arithmetic progression

#### Scenario: Rounding is rejected
- **WHEN** a proposed token value differs from its measured source
- **THEN** it is rejected unless the deviation is recorded with a reason

#### Scenario: Measurements are recorded
- **WHEN** a token is defined
- **THEN** its source in the reference is recorded, so the value can be re-verified later

### Requirement: Measurements are extracted mechanically and are re-runnable
The reference's values SHALL be extracted by tooling that parses its stylesheets, not transcribed by hand. The extractor SHALL record, for every declaration, its source file, selector, property, value and enclosing media query, and SHALL produce both a committed human-readable record and a machine-readable form. Re-running it against an unchanged reference SHALL produce identical output.

#### Scenario: Extraction is generated, not transcribed
- **WHEN** the measurement record is produced
- **THEN** it is generated by the extractor from the reference's stylesheets
- **AND** it can be regenerated at any time

#### Scenario: Output is stable
- **WHEN** the extractor is re-run against an unchanged reference
- **THEN** its output is identical to the committed record

#### Scenario: Extractor is verified against a sample
- **WHEN** the extractor's output is compared with a hand-checked sample of components
- **THEN** no declaration is missing, duplicated or attributed to the wrong source

#### Scenario: Built values can be diffed against sources
- **WHEN** a component's implemented values are compared against its extracted source measurements
- **THEN** the comparison is performed mechanically
- **AND** any difference that is not a recorded deviation is reported as drift

### Requirement: Responsive values follow the reference, per breakpoint
Responsive behaviour SHALL reproduce the reference's own behaviour at each breakpoint. Where the reference overrides a value within a media query, the token set SHALL carry that per-breakpoint value; where a value holds at every width, it SHALL hold at every width. A responsive step SHALL NOT be introduced for a value the reference does not vary.

#### Scenario: Breakpoint context is captured
- **WHEN** a measurement is extracted
- **THEN** the media-query context it appears in is recorded with it
- **AND** the record distinguishes values that hold at all widths from those overridden at a breakpoint

#### Scenario: Reference override is reproduced
- **WHEN** the reference overrides a value at a breakpoint
- **THEN** the token set carries that value at that breakpoint

#### Scenario: Invented responsive step is rejected
- **WHEN** a responsive variation is proposed for a value the reference holds constant
- **THEN** it is rejected unless recorded as a deliberate deviation with a reason

#### Scenario: Non-resizing component is not treated as a gap
- **WHEN** a component keeps the same dimensions at every viewport width in the reference
- **THEN** its implementation does the same, and this is not recorded as a defect

### Requirement: Layered token architecture
Tokens SHALL be organised as primitive values, semantic role aliases, and component-scoped tokens. Components SHALL consume semantic or component tokens only, never primitive tokens and never literal values.

#### Scenario: Component consumes only role-based tokens
- **WHEN** a component's styles are inspected
- **THEN** every colour, spacing, size, radius, border, shadow, font and duration value resolves through a semantic or component token
- **AND** no literal value appears in the component's styles

#### Scenario: A component may carry its own token
- **WHEN** a component needs a value no semantic role expresses
- **THEN** a component-scoped token is defined for it rather than a literal value being used

### Requirement: Token coverage
The token set SHALL cover colour (surfaces, text, borders, accent, status, and translucent surface tints), typography (family, size, weight, line-height, letter-spacing, and text-transform), spacing, sizing, border radius, border width, elevation, motion, layering, responsive breakpoints, and minimum touch target size.

#### Scenario: Every visual dimension is tokenised
- **WHEN** a component is authored against the system
- **THEN** it can express its full appearance without introducing a value outside these categories

#### Scenario: Breakpoints are tokens
- **WHEN** a component adapts to viewport width
- **THEN** it does so using a breakpoint token rather than a literal width

### Requirement: One design with complete light and dark schemes
The system SHALL define exactly one design, with a complete set of semantic token values for both a light and a dark colour scheme. The scheme SHALL be selected by an attribute on the document root and SHALL be switchable without a reload. No second design or theme pack SHALL be defined.

#### Scenario: Both schemes complete
- **WHEN** either colour scheme is active
- **THEN** every semantic token resolves, and no interface element renders with an unresolved value

#### Scenario: Completeness is validated
- **WHEN** a semantic token is missing from either scheme
- **THEN** validation fails and names the missing token and scheme

#### Scenario: Live scheme switch
- **WHEN** the colour-scheme attribute on the document root changes
- **THEN** the interface adopts that scheme immediately without a reload or component remount

### Requirement: Interactive accent is distinct from status colours
The interactive accent SHALL be visually distinct from the live, error, warning and success colours, differing from the error and live colours by at least 60 degrees of hue, remaining distinguishable under common colour-vision deficiencies, and meeting 4.5:1 as text and 3:1 as a focus indicator in both schemes.

#### Scenario: Accent is not confusable with an error
- **WHEN** an accent-coloured interactive element and an error-coloured element appear together
- **THEN** they are distinguishable by hue, and the accent does not read as an error or a live indication

#### Scenario: Hue separation is validated
- **WHEN** the accent falls within 60 degrees of the error or live colour
- **THEN** validation fails and reports the measured separation

### Requirement: Contrast compliance
Text and meaningful non-text elements SHALL meet WCAG 2.2 level AA contrast in both colour schemes: at least 4.5:1 for body text, 3:1 for large text, and 3:1 for interface components, focus indicators and meaningful graphical objects, measured against the token-defined surface behind them.

#### Scenario: Contrast verified across schemes
- **WHEN** the contrast of every documented token pairing is computed for each scheme
- **THEN** every pairing meets its applicable threshold
- **AND** any failing pairing is reported with its measured ratio, threshold and scheme

#### Scenario: Reference values that fail are corrected
- **WHEN** a value measured from the reference fails its contrast threshold
- **THEN** it is adjusted to meet the threshold, and the deviation is recorded with its reason

### Requirement: Token source of truth and generated output
Tokens SHALL be authored in a single machine-readable source, and the stylesheet consumed at runtime SHALL be generated from it rather than hand-maintained. The generated output SHALL be committed so that no token build step is required for an ordinary application build.

#### Scenario: Generated output matches the source
- **WHEN** the generator runs against the committed token source
- **THEN** its output is identical to the committed generated stylesheet
- **AND** a check fails when the two diverge

### Requirement: Typefaces are bundled
The typefaces the design requires SHALL be self-hosted and bundled. No network font request SHALL be made at runtime, and each font role SHALL declare a platform fallback stack. Character coverage SHALL include every glyph the supported locales require.

#### Scenario: Typography renders offline
- **WHEN** the application starts with no network connectivity
- **THEN** all text renders in the intended typefaces

#### Scenario: Locale glyph coverage
- **WHEN** text is rendered in any supported locale
- **THEN** every character renders in the intended typeface without substitution

### Requirement: Motion honours reduced-motion preferences
Animation and transition values SHALL be tokens, and when the system requests reduced motion those tokens SHALL resolve to values that eliminate non-essential motion without removing any state indication.

#### Scenario: Reduced motion suppresses transitions
- **WHEN** the system requests reduced motion
- **THEN** components complete state changes without animated transitions
- **AND** no component loses a state indication as a result
